# 通用流程契约：按能力接入，不按项目身份分流

这是供任意同类工程复用的CI流程。调用方选择技术栈与验证能力；模板不读取仓库身份来决定运行、跳过、审计阈值、异常豁免或发布行为。

## 不可变的边界

- `profile` 仅表示 `node`、`python`、`docs` 技术档位，不是用户项目编号或仓库清单。
- 版本、包管理器、锁文件、工作目录、检查命令、超时及报告标识均由明确的通用inputs传入。
- 不以仓库名、owner、owner/repo白名单、remote URL或业务项目特例选择行为；不提供`repository`、`owner`、`project-id`之类路由input。
- 工作目录是调用方选择的执行位置，不是模板内置的“某仓库对应某目录”映射；`artifact-key`只用于区分同run的报告，不改变质量策略。
- 质量、skip/cancel、漏洞、权限规则对相同能力配置一致。漏洞例外是调用方显式维护的受审阅策略，默认空；不能按项目身份暗中放宽。
- 跨仓库`uses`中的模板地址与固定Action地址是依赖来源，不是允许哪些调用项目的白名单。调用仓库更名或转移owner后，同样的能力配置应继续成立，受GitHub实际可见性与Actions策略约束。
- 公开文档使用技术档位和泛化命令。内部调研表是设计证据，不会被运行时读取，也不作为默认配置生成器。

## 规范流程

事件触发 → 选择适用技术档位 → 验证配置与锁 → 准备一次环境 → 静态检查 → 单元测试 → 构建 → 必要轻集成/浏览器 → 漏洞门禁 → 完成证明 → 固定`Gate`汇总。

有的能力对项目不适用时，由调用方配置明确表达；模板不猜“哪个名字的仓库可以少测”。纯资料和零依赖插件不执行无意义依赖安装。无代码且无待验证契约的仓库可以不接入。

未来如果增加变更范围优化，只接受调用方显式提供的技术路径/依赖关系规则；共享配置、锁、未知diff或查询失败默认执行。规则在已触发workflow内判定，最终Gate审计计划和结果；禁止维护中央项目清单或以顶层paths跳过required入口。当前候选没有自动路径筛选，避免给短CI增加派发及判断成本。

## 本地复核

运行`python3 tools/check_portability.py`。它检查公开workflow、调用样例与辅助脚本中的常见仓库身份上下文、环境变量、路由inputs和remote URL读取。工具没有用户项目名单、不访问GitHub、不参与项目运行时分流。静态模式检查不能证明任意混淆代码没有身份依赖，因此仍需正常代码审阅。

本次复核：4个模块、5个调用样例与2个辅助脚本没有仓库身份选择机制。四个运行时模块和两个辅助检查脚本保持不变；五个调用样例已固定真实公开SHA。新增这份契约、外部实践研究、本地维护检查及独立维护workflow。
